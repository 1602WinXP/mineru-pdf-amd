# 第一轮部署发现的技术解析

> 对 22.04 + ROCm 7.1.1 部署中 10 个发现问题的深度补充。每一条包含："怎么回事"（背景知识）、"为什么会踩坑"（根因分析）。

---

## 发现 3-4：rocminfo / rocm-device-libs "降级"

**怎么回事**：Ubuntu 22.04 官方源中 `rocminfo` 版本为 `5.0.0-1`，24.04 为 `5.7.1`。这些版本远早于 librocdxg 架构（2025 年底引入），完全不包含 WSL2 GPU 虚拟化检测逻辑。必须替换为 ROCm 7.x 仓库的版本（如 `1.0.0.70101-38~22.04`）。

**为什么会踩坑**：AMD 在 ROCm 仓库中重新启动了自己的版本号方案（`1.0.0.xxxxx`），而 Ubuntu 沿用旧版命名（`5.x`）。APT 只看数字大小，认为 `5.0.0` > `1.0.0`，拒绝"降级"。需要 `--allow-downgrades` 或 APT Pinning 解决。

**APT Pinning 替代方案**：创建 `/etc/apt/preferences.d/rocm-pin-600`：
```text
Package: *
Pin: release o=repo.radeon.com
Pin-Priority: 600
```
此后 `apt install rocminfo` 会自动选择 AMD 版本，无需每次手动指定版本号。

**rocm-device-libs 同理**：系统自带的 `5.0.0` 同样不包含 gfx1201 等新架构的 bitcode 文件，HIP 编译器会报 `cannot find ROCm device library`。

**Ubuntu 26.04 展望**：Canonical 计划在 26.04 LTS Universe 源中集成 ROCm 7.1.0，届时不再需要手动降级。但截至 2026-03 仍有包未就绪（核心 `rocm` 元包缺失），**现阶段不推荐依赖此方案**。

## 发现 5：hipsparselt-dev 缺失

**怎么回事**：PyTorch ROCm 版在编译时默认链接了 `hipSPARSELt`（AMD 稀疏矩阵加速库）。其 CMake 导出文件 `Caffe2Targets.cmake` 中硬编码了 `roc::hipsparselt` 依赖。如果系统只装了基础 ROCm 运行时，CMake 在 configure 阶段就会报 `target was not found`。

**为什么会踩坑**：ROCm 将底层库拆分得非常细（`hipBLAS`、`hipSOLVER`、`hipSPARSE`、`hipSPARSELt` 等）。许多教程作者通过 `rocm-hip-sdk` 元包全装了开发组件，未意识到 `hipsparselt-dev` 是个独立碎包。

## 发现 6：cmake 4.0 HIP 配置

三个独立问题，各有原因：

**PATH 必须包含 `/opt/rocm/bin`**：CMake 内部调用 `hipconfig --rocmpath` 探测 ROCm 安装目录。WSL2 默认不将 `/opt/rocm/bin` 加入 PATH。

**必须显式指定 `CMAKE_HIP_ARCHITECTURES`**：实体 Linux 上 CMake 通过 `rocm_agent_enumerator` 自动检测 GPU 架构。WSL2 虚拟化隔离下该工具经常失效，返回空结果导致 CMake 报错。

**不能设 `CMAKE_HIP_COMPILER=hipcc`**：CMake 内部模块 `CMakeDetermineHIPCompiler.cmake` **硬编码拒绝 `hipcc`**——检测到编译器名包含 `hipcc` 时直接 `FATAL_ERROR`。现代 CMake 要求直接使用底层 Clang（`amdclang++`），不能通过 `hipcc` Perl 包装器套娃。

## 发现 7：pyproject.toml License 字段

**怎么回事**：Python 打包标准从 PEP 621（`license` 必须是字典 `{text = "..."}`）过渡到 PEP 639（允许直接写字符串 `license = "Apache-2.0"` + 单独 `license-files`）。vLLM 的 `pyproject.toml` 用了 PEP 639 新格式，但旧版 setuptools 的校验器只认 PEP 621 格式。

**为什么会踩坑**：vLLM 官方已在 PR #17389 修复——强制要求 `setuptools >= 77.0.3`（该版本完整支持 PEP 639）。但旧版 commit（如教程推荐的 `357fddf61`）仍需要手动修改。

**推荐修复**：升级 setuptools 而非修改 pyproject.toml：
```bash
pip install --upgrade "setuptools>=77.0.3" setuptools_scm wheel
```

vllm 最新 main（commit `193ce8812`+）已原生支持。

## 发现 8：rocm.py WSL2 补丁 Bug

**怎么回事**：教程提供的正则补丁使用 `sed` 或 Python `re.sub` 替换 `_get_gcn_arch()` 函数体时，贪婪匹配跨越了函数边界，意外删除了后续的模块级常量定义（`_ON_GFX942`、`_ON_GFX950`、`_ON_GFX12X` 等），导致 `from vllm.platforms.rocm import _ON_GFX942` 时报 `ImportError`。

**为什么会踩坑**：正则表达式写得过于宽泛（如 `.replace("def _get_gcn_arch", "def _get_gcn_arch\n    return ...")`），缺乏对函数结束位置的精确判断。

**正确做法**：仅替换函数内部逻辑，保留函数签名和后续所有常量行。

**更重要的发现**：vllm 最新 main 的 `_get_gcn_arch()` **已经自带 torch.cuda 回退**——amdsmi 失败后自动调用 `torch.cuda.get_device_properties("cuda").gcnArchName`。在最新 vllm 上，**rocm.py 根本不需要 WSL2 补丁**。这是教程推荐旧 commit 的另一个代价。

## 发现 9：PyTorch 被覆盖（Triton 命名空间冲突）

**怎么回事**：安装 `mineru[core]` 或 `flash_attn` 等包时，pip 依赖解析器发现这些包声明了 `torch` 依赖，就去 PyPI 拉取 CUDA 版 torch（如 `2.11.0+cu130`），覆盖掉已安装的 ROCm 版（`2.11.0+rocm7.1`）。

**Triton 冲突的根因**：`pytorch-triton-rocm`（ROCm 专用 Triton）和 `triton`（NVIDIA 原版 Triton）在 `site-packages` 中的**物理文件夹都叫 `triton/`**。两个不同的 pip 包写同一个目录，必然相互覆盖。执行 `pip uninstall triton` 会连 ROCm 版编译的 `.so` 文件一起删除。

**正确修复顺序**：
```bash
# 1. 先装回 ROCm 文件
pip install --force-reinstall pytorch-triton-rocm --index-url https://download.pytorch.org/whl/rocm7.1
# 2. 再清理冲突包的元数据（不会删文件）
pip uninstall -y triton triton-rocm
# 3. 切勿手动删除 site-packages/triton/ 目录
```

## 发现 10：amdsmi 在 WSL2 中永远不可用

**怎么回事**：`amdsmi` 依赖 Linux 原生的 KFD（Kernel Fusion Driver）驱动和 `/dev/kfd` 设备节点。WSL2 通过微软 DXG 桥接器间接操作 GPU，不存在 KFD。因此 amdsmi 在 WSL2 中**永远报 Error Code 34**。

**影响**：无。vllm 平台检测已通过补丁绕过 amdsmi。`/opt/rocm/share/amd_smi` 目录存在与否、是否安装 Python 版 amdsmi，都不影响最终运行。

---

## 附加发现：snap 在 WSL2 中不可用

WSL2 默认不启动 systemd（需 `/etc/wsl.conf` 配置 `[boot] systemd=true`），且 snapd 的 mount namespace 在 WSL2 内核中受限。**所有 `snap install` 命令在 WSL2 中应避免使用。**

cmake 需从 Kitware GitHub 下载二进制包替代：
```bash
wget https://github.com/Kitware/CMake/releases/download/v4.0.0/cmake-4.0.0-linux-x86_64.tar.gz
tar -xzf cmake-4.0.0-linux-x86_64.tar.gz
sudo cp -r cmake-4.0.0-linux-x86_64/bin/* /usr/local/bin/
sudo cp -r cmake-4.0.0-linux-x86_64/share/* /usr/local/share/
```
