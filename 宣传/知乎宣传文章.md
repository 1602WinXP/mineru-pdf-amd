如果你是 AMD 显卡（RDNA 2/3/4 架构）用户，在接触目前最强的开源文档解析引擎 **MinerU** 时，大概率会遇到类似的起步挑战。官方团队目前主要聚焦于模型核心效果和解析能力的迭代，文档以主流的 NVIDIA / CUDA 平台为主，其他算力生态则通过 Discussions 板块鼓励社区共同建设。此前，社区已经涌现出非常有参考价值的适配探讨（如 healy-hub 针对 MinerU 2.x 的优秀分享）。但 MinerU 3.x 升级了底层依赖与加速套件，老教程在新架构下需要不少调整。

## 🛠️ 技术挑战：AMD 显卡在 WSL2 上的四道坎

为什么在 AMD 显卡上部署 MinerU 如此困难？因为我们不仅要面对 ROCm 生态的碎片化，还要在 Windows WSL2 的虚拟化环境下解决底层硬件交互的硬伤。这次部署中，我们合力攻克了四个核心技术阻碍：

### 1. 虚拟化环境的"断头路"：KFD 驱动与 PyTorch 崩溃

原生 Linux 上 ROCm 依赖内核级驱动 KFD。但 WSL2 中没有 KFD，而是通过微软和 AMD 共同提供的 `librocdxg`（DXCore）技术将显卡资源间接桥接给 ROCm。**PyTorch 2.12.0 起默认集成 `rocprofiler`，启动时会查询 KFD 拓扑结构**。WSL2 中查不到，PyTorch 就直接闪退。

**解决办法**：WSL2 环境严格锁定 PyTorch 在 **2.11.0**——这个版本避开了强制的 `rocprofiler` 检测。

### 2. amdsmi 报错 + 循环导入：vLLM 的双重识别硬伤

vLLM 在运行视觉大模型（VLM）时，默认调用 `amdsmi` 库来检测当前是否属于 ROCm 平台。但 WSL2 下 `amdsmi` 拿不到底层驱动接口会初始化报错，导致 vLLM 误判平台没有 GPU，直接抛出 `Device string must not be empty`。

更深层的坑是 `vllm/platforms/rocm.py` 中 `logger.warning_once()` 触发 `from vllm.distributed.parallel_state import ...` 形成**循环导入**——即使你修好了 amdsmi 兜底，子进程（EngineCore）的 `current_platform` 仍会被设为 `UnspecifiedPlatform()`，然后 `NotImplementedError`。

**解决办法**：两个补丁缺一不可。`platforms/__init__.py` 加 `torch.version.hip` 兜底；`platforms/rocm.py` 把 `logger.warning_once()` 换成 `sys.stderr.write()` 断开循环导入链。

### 3. MIOpen 冷启动：突如其来的"7 秒延迟"

AMD 的 MIOpen（类似 NVIDIA 的 cuDNN）有一个机制：遇到新尺寸的卷积计算时，会在后台进行内核搜索（冷启动），导致每次解析新排版的页面时出现 1-7 秒不等的卡顿。

**解决办法**：在 MinerU 图像输入端将页面尺寸对齐到 32 像素，并对 batch 进行零填充，规避会触发冷启动的尺寸组合；同时用 `cache_warmer.py` 提前把常用尺寸搜索好存入磁盘缓存。预热后冷启动从 1-7 秒缩短到 **30 毫秒** 级别。

### 4. WSL2 网络与防火墙：你以为代理设好了，结果 Hyper-V 在拦截

镜像网络模式（`networkingMode=mirrored` + `firewall=true`）开启后，**Hyper-V 防火墙默认阻止所有进入 WSL2 的入站连接**——vllm engine 子进程间 IPC 通信被切断、Windows 浏览器访问不到 WSL 里的 WebUI。Clash TUN 用户还要把默认 9000 的 MTU 改成 1500，否则 TLS 握手后就静默卡死。这些都不是一眼能看出来的，必须老老实实把网络层准备好。

**解决办法**：管理员 PowerShell 执行 `Set-NetFirewallHyperVVMSetting -Name '{40E0AC32-...}' -DefaultInboundAction Allow`，并把 Clash TUN MTU 调成 1500。

## 📊 成果验收：AMD 显卡的逆袭

环境搭好后，我们用 `example.pdf`（13 页的复杂文档）对本地 **AMD RX 9070 (16GB)** 和云端 **NVIDIA A10 (24GB)** 进行了对比测试：

- **VLM 大模型推理（提取表格与文字）**：A10 稍快，约 5 秒；RX 9070 紧随其后，约 6 秒。
- **Layout 版面与 OCR 阶段**：**RX 9070 爆发了**。凭借 640 GB/s 高显存带宽，处理速度达到 **61 it/s**（路径 A）/ **65-71 it/s**（路径 B，ROCm 7.2.1 + hipBLASLt 在线调优）；A10 只有 **36 it/s**。
- **总耗时**：两者完成解析的时间都在 **6-7 秒** 左右，输出的 Markdown 和公式质量完全一致。

只要环境和补丁打得对，AMD 显卡本地运行的效率完全不输云端的主流 NVIDIA 推理卡。

## 🧭 读者的快速部署指南

想在本地把 AMD 显卡用起来，按以下步骤切入：

1. **检查显卡兼容性**：需要 RDNA2/3/4 架构（RX 6000 / 7000 / 9000 系列桌面卡，显存 ≥ 8GB）。
2. **选择部署路径**：
   - **路径 A（推荐，稳）**：Ubuntu 22.04 + ROCm 7.1.1
   - **路径 B（较新）**：Ubuntu 24.04 + ROCm 7.2.1，额外打几个 ROCm 头文件补丁
   - **避坑**：Ubuntu 24.04 + ROCm 7.1.1 是死路（LLVM 20 不兼容），不要尝试
3. **按教程部署**：克隆仓库，按 [MinerU 本地部署教程](https://github.com/buptanswer/mineru/blob/main/%E6%95%99%E7%A8%8B/MinerU%E6%9C%AC%E5%9C%B0%E9%83%A8%E7%BD%B2%E6%95%99%E7%A8%8B.md) 走完。
4. **日常使用**：部署好后，可以通过命令行、WebUI，或用仓库自带的 `mineru_api_client.py` 像调用官网 API 一样在局域网内远程调用。
